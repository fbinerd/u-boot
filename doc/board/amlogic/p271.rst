U-Boot for Amlogic P271
=======================

P271 is an Amlogic reference design used by TV boxes based on the GXLX
variant of the S905L SoC.  The hardware validated for this port has:

* Amlogic S905L quad-core Arm Cortex-A53 SoC at up to 1.2 GHz
* Mali-450 MP2 GPU
* 1 GiB LPDDR3
* 10/100 Ethernet
* HDMI output
* USB 2.0 host ports
* eMMC and microSD storage
* SSV6006C SDIO Wi-Fi

The Wi-Fi device requires operating-system support and firmware; U-Boot does
not depend on it.  The device tree intentionally follows the Linux mainline
P271 description instead of carrying register-level code from the legacy
vendor bootloader.

Build U-Boot
------------

Use a recent AArch64 cross compiler::

    $ make CROSS_COMPILE=aarch64-linux-gnu- p271_defconfig
    $ make CROSS_COMPILE=aarch64-linux-gnu- -j$(nproc)

Alternatively, use the reproducible container build environment::

    $ docker build -t uboot-amlogic-p271-mainline:2026.07 .
    $ docker run --rm --user "$(id -u):$(id -g)" \
        -e HOME=/tmp -v "$PWD:/workspace/u-boot" \
        uboot-amlogic-p271-mainline:2026.07 \
        bash -lc 'make O=build-p271 p271_defconfig && \
                  make O=build-p271 -j$(nproc)'

The resulting ``u-boot.bin`` is BL33.  On GXL/GXLX systems, BL33 must be
packaged with board-compatible Amlogic BL2, ACS/DDR training data, BL30 and
BL31 firmware.  The firmware extracted from the original P271 image can be
used for board bring-up; it is not part of the GPL U-Boot source tree.

The experimental open source GXL SPL does not currently expose an LPDDR3
memory type.  Until P271 LPDDR3 training is implemented and validated, retain
the board-specific factory BL2/ACS data for hardware tests.

RAM-only USB test
-----------------

``tools/boot_p271_ram.py`` implements the volatile GXL USB load sequence.  It
accepts only the SHA-256-verified factory BL2 from the tested P271 unit and
uses bounded transfers for the TPL.  The helper calls only the pyamlboot RAM
write, identify and run operations; it has no persistent-storage operation.

Enter the BootROM USB stage before using it.  The response from ``identify``
must report ROM 2.4, stage 0.0.  The vendor ``update`` command can instead
leave this unit at stage 0.16, which cannot accept the initial BL2 write.

Do not write an untested image to eMMC.  Test from removable media first and
retain a complete dump of the original bootloader area.

The eMMC fitted to the validated unit operates reliably with single-block
commands but rejects the controller's CMD18/CMD25 multi-block transfers.
The U-Boot-specific device-tree sets ``u-boot,max-block-count = <1>`` so the
block layer transparently splits larger reads and writes into sector-sized
operations.  This does not affect the Linux device tree or other Meson boards.

Default boot and TFTP environment
---------------------------------

The default environment boots the untouched factory Android image directly
from eMMC device 2.  The offsets are taken from the verified 7.3 GiB dump of
this exact board: partition ``boot`` starts at LBA ``0x2ae000`` and occupies
``0x8000`` sectors.  U-Boot validates the Android header and inner legacy
uImage magic, decompresses the vendor multi-DTB payload, validates the first
DTB (P271 board ID 1), and only then runs ``bootm``.  Any failed validation
returns to the command prompt instead of falling through to network boot.

The automatic command is ``run boot_emmc_original``.  ``run boot_tftp`` is a
manual development path and loads ``Image``,
``meson-gxlx-s905l-p271.dtb`` and ``android-initramfs.cpio.gz`` from
``192.168.1.10``.  The board defaults to ``192.168.1.199/24`` with gateway
``192.168.1.254``.  TFTP is deliberately not an automatic fallback: a missing
server must never delay normal factory boot.

These offsets and component sizes describe the preserved factory image only.
If the factory ``boot`` partition is ever replaced, regenerate the environment
from the new Android boot header rather than reusing the constants blindly.

The factory boot path needs ``CONFIG_CMD_UNZIP`` because the Android v0
``second`` component is a gzip-compressed Amlogic multi-DTB container.  The
verified board-ID-1 DTB begins at offset ``0x800`` in its uncompressed
``0x39800``-byte payload.  The inner kernel is a 32-bit legacy uImage, so this
configuration also retains legacy-image and AArch32 handoff support.

After packaging BL33, extract the resulting FIP again and compare BL2, BL30,
BL301 and BL31 byte-for-byte with the factory inputs.  This catches accidental
firmware substitutions before a RAM-only hardware test.  A successful local
build and package validation does not replace that hardware test and is not
authorization to write the image to eMMC.
